# ADR 0008：私有预览的现代 Chrome 优先策略

- 状态：已接受
- 日期：2026-09-07
- 依据：维护者确认产品尚未对外开放、仅本人使用，要求更积极地迁移与优化；本轮仅授权文档规划，不执行编码、安装或数据变更。
- 关系：补充 ADR 0004、0005、0006、0007 的兼容性和演进策略，不改变扩展唯一产品、同页 App、mock/real 与 Worker 边界。

## 背景

为不存在的旧版用户保留多套实现会增加私有预览的维护成本。外部指南提出的旧浏览器更新风险需要在公开交付前重审，但不应阻止开发期主动迁移。外部 API 核对见 [研究记录](../research/chrome-extension-ai-guidance.md)；官方可用性描述仍需目标环境验证。

## 决策

- 私有预览只追随维护者使用的最新 Chrome Stable，不承诺旧版本或其他浏览器。下一次扩展壳迁移以 `minimum_chrome_version: "148"` 为起始下限；实际所需 API 更高时随验证上调。此值是迁移计划，不表示所有 148+ 版本都经过支持测试，也不表示本机已满足要求。
- 每轮迁移固定 Chrome 完整版本、OS、WXT 与测试工具版本；先验证再移动基线，不采用无记录的自动追新。实验 flag/Canary 可作隔离研究，不作为日常可用结论。
- 扩展 adapter 以原生 `browser.*` 和 Promise 异步接口为目标；核对 WXT 包装与产物后删除已无必要的旧版 shim、双路径和仅为旧版本存在的依赖。不能为统一命名空间把 BroadcastChannel/Worker 通信改走 Service Worker。
- `runtime.onMessage` 的真正异步请求优先 Promise 响应，同步处理无需强改 `async`；按消息类型明确路由，保留 schema、sender、owner、超时与结构化错误。目标环境的灰度能力未启用时，优先升级/等待可用基线；确需短期桥接则单点隔离、记录移除条件，不默认永久维护两套协议。
- 原生 Dialog/Popover、Anchor Positioning、Container Queries 和简单 CSS 动效优先替换等价自建实现；基线已覆盖的旧浏览器 polyfill 可以删除。焦点管理、键盘、低性能、减少动态/透明度及错误降级不是旧版兼容包袱，不能删除。
- 允许内部接口破坏性重构和替换已锁定依赖，不要求长期双轨兼容；每次围绕明确收益和一组回归测试实施。布局/Link 配置等个人数据须提供迁移或备份恢复方案；废弃 mock 数据重置需明确告知并在执行前取得同意，不能静默清空。
- 官方 skill 与 Chrome DevTools MCP 作为优先开发工具接入方向；仍先审查来源、版本、遥测和 profile 范围，实际安装及连接另行执行。隔离 profile 与无调试器生命周期对照不因私有预览省略。

## 后果

- 开发期可以用抬高浏览器下限代替历史浏览器兼容层，集中验证一个真实环境；每次 Chrome 更新仍需核心回归。
- 核心能力缺失可明确拒绝并提示更新，不必为所有缺失能力写 polyfill；硬件/配额/授权等运行时探测与可解释失败继续保留。
- 前端/扩展壳迁移前移到 Phase 1；真实文件、引擎、后台生命周期的完整验收仍按 Phase 2/G2 执行。具体工作顺序只在 [开发蓝图](../DEVELOPMENT_BLUEPRINT.md) 维护。
- 对外测试或发布前必须重新决定版本支持窗口、数据迁移、权限和安装/升级承诺，不能直接沿用私有预览策略宣称公众支持。

## 替代方案

- 不采用“为潜在旧用户默认保留所有 fallback”：没有实际用户收益，却延长迁移期。
- 不采用“一次性升级所有依赖或全面重写”：新版本并非收益证据，框架大版本升级应另有具体问题与成本评估。
- 不采用“私用即可跳过安全与质量”：用户自己的文件、浏览器权限和数据同样需要保护。
